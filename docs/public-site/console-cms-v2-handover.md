# Console CMS: handover for content contract `audoryn.public.v2`

> The Console works from its copy, `Audoryn-Console/docs/integration/public-content-v2-handover.md`, from 11 October 2026 onwards. Keep the two in step when the contract changes.

Written 11 October 2026, at the end of AgentGate Phase 10 (branch `feature/public-site-v2`).
For whoever stabilises the Console CMS (Console phases C1–C5). The owner adds Console-side
requirements in [section 10](#10-owner-requirements-for-the-console).

The AgentGate public site has been rebuilt and reads only `audoryn.public.v2`. Until Console
publishes v2 content, the site shows its built-in v2 documents (the approved copy), so nothing is
broken in the meantime. Console must now produce, edit, preview, validate and publish v2.

## 1. In one page

| Topic | v1 (today in Console) | v2 (what the site reads now) |
|---|---|---|
| Content of a page | One document plus 17 hidden `/content-fields/...` copy pages, 656 fragments | One document per page; nothing hidden |
| Structure | `profile` + generic `sections[]` + per-profile lists | `page` + fixed, named `sections` per page template |
| Editor labels | Generated from component names ("field sot cm") | `title` and `description` on every field in the schema |
| Images | `{asset_id, role}` | `{asset, alt}`: alt text is required and stored with the content |
| Links | `{label, destination}` | `{label, href}`: a site path or an `https://` URL |
| Shared site text | global `public-branding` (v1) | global `public-site` (the v2 site document) |
| Navigation | Console navigation `header` / `footer` | The same resources; used only when `public-site` is published too |
| `rendererContract` in a release | always `audoryn.public.v1` | must be taken from the payload: `audoryn.public.v2` |

### 2.1 Page templates

The schema lists them under `x-pages` (section keys) and `x-optional-sections`. Page order and
layout belong to the site; editors change content, list items and optional sections only.

| Page (`page`) | Path | Sections (all required unless noted) |
|---|---|---|
| `home` | `/` | hero, activity, decision, product, controlPath, policy, operatingModel, oversight, controls, connections, solutions, closing |
| `product` | `/product` | hero, workspace, workforce, runtime, intelligence, supervision, integrations, closing |
| `solutions` | `/solutions` | hero, solutions, closing |
| `security` | `/security` | hero, decision, controlPath, safeguards, record, closing |
| `pricing` | `/pricing` | hero, plans, sameModel, questions, closing |
| `resources` | `/resources` | hero, guides, library (optional), operators |
| `company` | `/company` | hero, about, portfolio, why, founder, closing |
| `privacy`, `terms` | `/privacy`, `/terms` | document |

The site document (`page: "site"`) holds the brand, the sign-in and get-started actions, an
optional announcement bar, the built-in navigation, interface labels, the vocabulary used in
demonstrations, and the not-found and unavailable texts.

### 2.2 Rules a schema cannot express (Console must enforce them too)

Errors are `{path, code}` only, never content, so they are safe to log and to show.

| Code | Rule |
|---|---|
| `invalid_format` | Plain text only: no `<` or `>`, no control characters or line breaks, no leading or trailing spaces. Templates must contain their placeholder (`{count}`, `{label}`, `{place}`). Code lines may be indented. |
| `duplicate_key` | `id` (or `key`) values are unique within each list. |
| `unsafe_link` | `href` is a site path (`/…`, not `//`, no backslashes, spaces or encoded slashes) or an `https://` URL without credentials. |
| `invalid_date` | Dates are real `YYYY-MM-DD` dates (legal effective date, article published date). |
| `contact_requires_link` | A pricing plan with availability `contact` has an action link. |
| `free_plan_must_be_free` | A plan with availability `free-signup` has `priceMinor` 0. |
| `duplicate_anchor` | An item anchor (below) does not repeat a section anchor or another item's anchor. |

Store v2 payloads **exactly as received**: do not add defaults, drop unknown-but-valid fields
or rename anything. (v1 passes payloads through a Pydantic `model_dump`, which adds defaults.)
The importer and the site both compare content, and a normalised copy looks like an edit.

### 2.3 Link anchors (`x-anchors`)

A link such as `/product#workforce` must land on something. The anchors of a v2 page are:

- every present section, at its key in kebab case (`controlPath` → `control-path`);
- the `id` of each item in `solutions.sections.solutions.items`, `privacy|terms.sections.document.clauses`
  and `article.sections.article.sections`.

`resources#library` exists only while articles are published. AgentGate's tests check that every
page renders exactly these anchors. Console's release validation (`release_graph.py`) reads
anchors from v1 `payload["sections"][].id` today and must use this rule for v2 pages.

## 3. What the site reads from a release

The verified delivery is unchanged: a storage origin with the `/cms-public/` prefix, no
redirects, SHA-256 checksums, 4 MiB per document, ETag revalidation, and refusal of stale
releases.

- **Page envelope:** `pageId`, `revisionId`, `locale`, `slug`, `title`, `contentType`, `rendererContract`, `blocks`, `seo`.
  - A v2 page has exactly one block, `{type: "PublicContent", content: {payload: <v2 document>}}`.
  - `rendererContract` must be `audoryn.public.v2`.
- **SEO** (unchanged): `metaTitle`, `metaDescription`, `canonicalUrl`, `openGraphTitle`, `openGraphDescription`, `openGraphImageAssetId`, `index`, `structuredData`.
- **Global content** `public-site` (locale `en`): the v2 site document. Navigation resources `header` and `footer` are applied **only when `public-site` is in the same release**, so navigation written for v1 can never point into v2 pages.
- **Navigation items**, as today:
  - `{id, parentId, position, label, destinationKind: page|path|url, destination, visible, openInNewTab, metadata}`;
  - `metadata.description` is the link description; on a top-level menu it is the menu introduction;
  - `metadata.sectionId` is an anchor (section 2.3). A footer top-level item is a group heading; its destination is not shown.
- **Assets:** every image referenced by `asset` (v2) must be in the release, ready and verified. The site rejects a page whose image is missing (notice `page_missing_media`).
- **Redirects:** unchanged.

### 3.1 How the site lays out navigation (so editors know what to expect)

- **Header bar:** the bar never grows.
  - With more menus, or longer labels, the space between the menus shrinks (28 px down to 12 px).
  - When even that does not fit, the bar switches to the Menu button.
  - Touch screens always use the Menu button.
- **Dropdown panel:** keeps one height. Up to 4 links: two columns. 5 or 6 links: three columns,
  with each title on one line and descriptions cut to two lines.
- **Footer:** groups stay on one row and narrow as groups are added; rows tighten as links are
  added. At the maximum (6 groups of 8 links) the footer grows from about 400 px to about 485 px.

How the site falls back:

| Situation | Result |
|---|---|
| Valid v2 page in the release | Rendered |
| Page is v1, or invalid v2 | Built-in v2 page (or the last valid version held in memory); the reason is logged as a code |
| Nothing published | Built-in site |
| A page the release no longer contains (other pages present) | 404 |
| Unknown path | 404 |
| Release unreachable | Last verified release |

  Say so next to the fields, and refuse more. Also tell editors that a menu with 5 or 6 links shows

- **Owner-requested changes:** section 10.

### C3: Visual preview

AgentGate's `/_cms/preview` already renders v2. Console's preview page today shows
"content inspection" only; C3 embeds the real site in an iframe. The handshake:

1. Console opens `<site origin>/_cms/preview` in an iframe. AgentGate must be configured with
   `PUBLIC_CONTENT_PREVIEW_ORIGIN=<Console origin>`.
2. The page posts `{type: "audoryn.cms.preview.ready", nonce}` to the parent, addressed to that origin.
3. Console replies to `event.source` with `{type: "audoryn.cms.preview", nonce, payload}`, where
   `payload` is the existing preview response, `GET /api/v1/cms/preview/{token}`:
   `previewMode: "content_inspection"`, `revision`, `assets` as `{assetId: https URL}`, `navigation`,
   `globalContent`, `pinnedReleaseVersion`, `unresolvedReferences`, `unresolvedAssets`.
4. The page accepts only a message from that origin, from its parent window, carrying its nonce.
   - It refuses `http:` asset URLs and any unresolved reference.
   - It renders v2 with the new site and v1 with the previous renderer.
   - It is `noindex`.

### C4: Releases and retiring v1

- **A v2 release contains:**
  - the nine page revisions;
  - global `public-site`;
  - navigation `header` and `footer` (rewritten for v2 by the importer);
  - the images the pages use.
- Leave out the 17 `/content-fields/...` pages and the v1 global `public-branding`.
- **Partial releases work page by page:** v2 pages render, and pages still on v1 show the built-in v2 page. A complete v2 release is the goal.
- **After the first v2 release is live:**
  - archive the `/content-fields/...` pages and `public-branding`;
  - stop accepting new v1 revisions (one release later, so you can roll back);
  - remove v1 validation after Phase 11.
- **Schema drift check:** before deploying a frontend change, compare AgentGate's
  `contract.v2.json` with Console's copy. Fail if they differ, or if published content fails the
  new schema. (A compatible change only adds optional fields or sections; anything else needs
  content published first, or v3.)

## 5. Importer: what it calls

`npm run site:import` in AgentGate `frontend/` (scripts `import-site-seed.mjs` and
`site-seed-importer.mjs`). It works by stable keys:

- a page by its path and locale;
- the site document by its global key;
- navigation by its key;
- an image by file name and checksum.

| Purpose | Call (prefix `/api/v1/cms`) | Notes |
|---|---|---|
| Inventory | `GET /assets`, `GET /pages` with `limit`, `offset` | Lists return `{items, total}`. |
| Page detail | `GET /pages/{id}?locale=en` | `revisions[]` with `id`, `revision` (number), `status`, `title`, `slug`, `locale`, `blocks`, `seo`. |
| New page | `POST /pages` `{title, slug, locale, content_type: "page", reason}` | Returns `{page, revision}` (an empty first draft). |
| New draft revision | `POST /pages/{id}/revisions` `{locale, title, slug, blocks, seo, based_on_revision_id, reason}` | Revisions are append-only; the previous one is kept. |
| Image | `POST /assets/upload-intents`, `PUT <signed URL>`, `POST /assets/{id}/complete` | `complete` verifies the stored bytes. |
| Site document | `GET /global-content?locale=en`, `PUT /global-content/public-site` `{locale, value, reason}` | |
| Navigation | `GET /navigations?locale=en`, `POST /navigations` `{key, name, locale, reason}`, `PUT /navigations/{id}/items` `{items, reason}` | Seed item IDs are stable UUIDs. |

The importer never calls submit, approve, schedule, publish or release endpoints (its tests
check this), and its request layer refuses any write to an approve, schedule, publish, restore,
withdraw or ready endpoint. Behaviour Console must keep:

- **v2 must be accepted on save.** Until C1 is done, Console rejects v2 payloads, so the importer
  is run only after C1.
- **Errors** are `{error: {code, message}}` with an `x-request-id` header. The importer prints the code, the status and the request ID only, never the message.
- **Repeated writes.** Every Console write needs an `Idempotency-Key` header (8–200 visible
  characters). Console replays the stored answer when the same key, path and caller repeat within
  an hour, and refuses the write if Redis cannot protect it. The importer derives its key from
  the import and the request, and still never retries a write itself. After any failure, run it
  again: it compares Console with the seed and continues. Reads are retried on transport errors
  and 502–504.
- **Conflicts stop the import before any write:**
  - `page_edited_in_console`: a v2 draft the importer did not write;
  - `global_edited_in_console`;
  - `navigation_edited_in_console`;
  - `page_has_scheduled_revision`;
  - `page_ambiguous`, `media_ambiguous`.

  Navigation that is not the importer's own (the v1 header and footer) is replaced only with `--replace-navigation`.
- **Receipt.** `content-seed/import-receipt.v2.json` (git-ignored) records what was written,
  so a later seed updates the importer's own drafts and nothing else. The output lists the
  release items for an editor to add after approval.
- **Interrupted image upload.** If a run stops between creating an upload intent and the upload
  itself, `complete` fails with `media_verification_failed`. Archive that asset in Console and
  run again.

## 6. Acceptance checks for the Console phases

1. Every valid v2 document is accepted; every invalid case is rejected with its path and code.
2. A saved v2 payload reads back byte-for-byte equal as JSON (no added defaults).
3. The schema endpoint returns the v2 contract with titles, help and `x-anchors`.
4. A release with v2 pages has `rendererContract: "audoryn.public.v2"` in its page index, and it includes their images.
5. Release validation rejects a navigation `sectionId`, or an in-page `href` anchor, that the target page does not have (section 2.3), and accepts every anchor used by the seed.
6. The editor can change every field of every template without leaving it invalid, can add and remove optional sections and list items within limits, and requires alt text for every image.
7. The visual preview shows a v2 draft in the real site through the handshake; a message from any other origin or with a wrong nonce is ignored.
8. `npm run site:import -- --plan` against the local Console reports no conflicts other than the expected v1 navigation; `--apply --replace-navigation` creates the drafts; a second `--apply` writes nothing.
9. After approval and publication, every AgentGate page shows Console content: the response has no `default_used` notices, and a headline changed in Console appears on the site.
10. Removing a page from the release returns 404; an invalid page keeps the last valid version.

## 7. Local end-to-end procedure (C5 and AgentGate Phase 11)

1. Console (local), after C1–C4: start backend and frontend as usual.
2. AgentGate `frontend/`:

   ```powershell
   npm run site:seed -- --check                # seed matches the built-in content
   npm run site:import                          # offline check, no network
   $env:CONSOLE_IMPORT_ORIGIN = 'http://localhost:<console port>'
   $env:CONSOLE_IMPORT_TOKEN = '<a local editor token, typed into this shell only>'
   npm run site:import -- --plan                # reads only
   ```

3. In Console: review the nine drafts, the site document and the navigation, then approve them.
   Create a release from the listed items, then publish it.

   ```powershell
   $env:PUBLIC_CONTENT_ENABLED = 'true'
   $env:PUBLIC_CONTENT_ORIGIN = '<storage origin>'
   $env:PUBLIC_CONTENT_PREVIEW_ORIGIN = '<Console origin>'
   npm run build
   npm run preview
   ```

   Open every page and check that the content comes from Console (checks 9 and 10).
5. Then run `npm run verify:site` and `node scripts/verify-public-host.mjs`.

## 10. Owner requirements for the Console

Recorded 11 October 2026.

### 10.1 Edit published content (in the CMS work, C2)

Today a published page is locked. The editor says "Save a new revision", but hides the Save
button, so nothing can be changed. The backend can already copy a revision into a new draft
(`POST /revisions/{id}/restore`); the page editor has no button for it.

- **Edit:** a published page shows **Edit**. Anyone with edit access can use it; no request or
  approval is needed to start. It creates a draft copy of the published revision (`based_on` the
  published one). The live site keeps showing the published version.
- **Publishing:** the draft goes through the usual review, approval and publication (release).
  It replaces the published version only when it is published.
- **One open draft per page and locale:** if one exists, the button reads **Continue editing**.
- **Compare with published**, and **Discard draft** (the published version is never touched).
- **Site text and navigation:** they are edited in place, but the live site changes only when
  a release is published, because a release stores a snapshot of them. They therefore already act
  as drafts. What they lack: **Compare with published** and **Revert to published** (restore the
  published snapshot into the working copy).

### 10.2 Invite Console users and grant roles (after the CMS work)

Today the Administrators page can list users, assign and remove roles, suspend, sign out and
reset passwords, but cannot add anyone. The first owner is created with the command-line
bootstrap. An "invited" status exists, but nothing uses it.

- **Who can invite:** an owner, or anyone with `platform.administrators.manage`, enters email,
  name and roles, then invites.
- **The link:** the Console creates an invited account and a one-time link. The inviter copies the
  link and sends it themselves (no email service). The link works once and expires, for example after 72 hours.
- **Joining:** the person opens the link and sets their own password; the account becomes active.
  Nobody else ever sees the password.
- **Roles:** the 9 existing roles, with no custom roles.
- **Safety rules:**
  - You cannot grant a role above your own; only an owner makes owners.
  - The last owner cannot be removed or suspended.
  - Invitations can be cancelled and re-issued.
  - Everything is in the audit log.

### 10.3 Keep showing AgentGate data when AgentGate is down (after the CMS work)

Today summary reads are cached in memory for 30 seconds. Lists, details, search and security reads
are not cached at all, and a failed read shows "unavailable" with no data.

**Owner decision (option A): in memory only.** Decision 0001, Amendment 1 says "no customer data
copied into Console", so nothing is written to the Console database. This needs a small written
amendment, approved by the owner, because the in-memory copy is now kept longer and also covers
lists and details.

- **Last good answer:** Console keeps the last successful response for each read in memory,
  bounded by entry count and size, and discards it after 7 days. It is lost when Console restarts
  or redeploys; until AgentGate answers again, pages then show "unavailable" as today.
- **Show it, clearly marked:** on `timeout`, `unavailable`, `unreachable` or `rate_limited`, show
  that data with a banner: "AgentGate is unreachable. Showing data from <time> (<age> ago)." After
  about a day, the banner warns that the data is old.
- **Disable what needs AgentGate:** actions that depend on AgentGate are disabled, with the reason shown.
- **Different message for setup problems:** `unauthorized`, `unconfigured` and `invalid_response`
  say that the connection needs fixing, not waiting.
- **Health light:** a header indicator checks AgentGate, with a growing delay between failed
  checks, and recovers by itself.
- **Access:** the copy is shown only to people allowed to see that data today. Logs stay as now:
  operation, outcome, duration and request ID only.
- **Later, if restarts during outages matter:** store summary pages only in the database
  (option B). That would need its own amendment.

# Tests

## Test 1 - Show worker run outcomes and duration analytics [sanity]
Viewport: desktop
Covers: Performance workspace, GET performance route family, Worker summary, run success/failure rates, run durations
Description: Verifies completed and failed managed Runs become visible operational metrics without creating a worker score.

Setup:
1. Create one managed Worker and produce at least one COMPLETED Run and one FAILED Run for that Worker through the existing Jobs/Runtime workflow

Steps:
1. Open Performance
2. Inspect the top metrics and Worker summary row
3. Refresh the page

Expected: The Worker remains visible with the same Run counts, success/failure percentages and duration values after refresh, and the page states that no employee quality score is used.

## Test 2 - Keep governance outcomes separate from provider reliability
Viewport: desktop
Covers: blocked Action analytics, approval rate, tool reliability denominator, read-only performance behavior
Description: Verifies policy blocks and approval holds are visible but are not incorrectly counted as provider failures.

Setup:
1. Produce one managed provider Action that EXECUTES, one Action that is BLOCKED by policy, and one Action that is HELD for approval
2. Resolve at least one approval decision through the existing Approvals workflow

Steps:
1. Open Performance
2. Inspect Approval rate and Blocked actions
3. Inspect Tool reliability for the connected provider

Expected: Approval and blocked counts are visible, Tool reliability uses only executed/provider-failed attempts, and blocked or held governance outcomes are displayed separately from provider failures.

## Test 3 - Roll up departments and human-supervision signals
Viewport: desktop
Covers: department overview, escalation rate, incident rate, Worker-to-Agent incident mapping
Description: Verifies F19/F11 supervision events are summarized as operations data without changing those source records.

Setup:
1. Create managed Workers in at least two departments
2. Produce an escalation for one Worker and an Incident targeting that Worker's Agent Identity

Steps:
1. Open Performance
2. Inspect the Departments panel
3. Compare the affected Worker/department with the escalation and incident summary metrics

Expected: Departments are grouped by their existing Worker department, the affected Worker/department shows its supervision counts, and the source escalation and Incident remain unchanged in their original workspaces.

## Test 4 - Filter the recent Worker activity timeline
Viewport: desktop
Covers: recent activity projection across Runs, Actions, Escalations and Incidents, Worker filter
Description: Verifies a human can inspect one managed Worker's operational history without a new analytics write model.

Setup:
1. Produce recent Run and governance activity for two different managed Workers

Steps:
1. Open Performance
2. Set the Activity Timeline filter to the first Worker
3. Change the filter to the second Worker

Expected: Each filter shows only activity attributed to the selected Worker, with event kind/status and recent occurrence time visible.

## Test 5 - Use Performance with API v2 on mobile
Viewport: mobile
Covers: API v2 performance normalization, mobile Performance navigation, responsive metrics/worker/tool/activity views, bounded-window warning
Description: Verifies workforce operations analytics remain usable on a phone and the v2 contract renders the same canonical metrics.

Setup:
1. Have at least one managed Worker with Run and Action history

Steps:
1. Open mobile navigation → Performance
2. Switch Compatibility view to API v2
3. Review metrics, Worker summary, Tool reliability and Activity Timeline

Expected: The same canonical analytics remain visible with no horizontal page clipping; wide Worker data scrolls inside its table container, and any truncated source window is disclosed instead of silently treated as complete history.

## Test 6 - Recover an expired runtime lease
Viewport: backend
Covers: durable queue, lease expiry, restart recovery, checkpointed dispatch
Description: Verifies an interrupted managed Run is recovered without losing its Work Item.

Setup:
1. Create a due Work Item with an active dispatch and an expired lease

Steps:
1. Run the managed-runtime cron handler
2. Read the Work Item and runtime dispatch records

Expected: The Work Item is queued with recoveryCount incremented, claim and heartbeat cleared, lastCheckpoint set to recovered, and the dispatch delayed with bounded backoff.

## Test 7 - Fence stale workers and dead-letter repeated expiry
Viewport: backend
Covers: claim verification, heartbeat fencing, duplicate-run protection, dead-letter handling
Description: Verifies stale workers cannot keep executing and poison work does not retry forever.

Setup:
1. Create a running Work Item with a superseded claim token
2. Create another expired Work Item whose recoveryCount is 2

Steps:
1. Attempt a heartbeat with the old claim token
2. Run the managed-runtime cron handler for the repeatedly expired Work Item

Expected: The stale heartbeat is rejected with conflict; the repeatedly expired Work Item becomes dead_letter, its dispatch is removed, and a critical audit event is emitted.

## Test 8 - Hold and replay a GitHub issue write
Viewport: backend
Covers: F22 side-effect expansion, bounded input, payload idempotency, human approval, credential reauthorization
Description: Verifies the first controlled provider write cannot execute without an approval record and cannot change payload across retries.

Setup:
1. Connect a GitHub repository with a write-capable credential
2. Declare `github.repository.issues.create` for an active Agent
3. Configure the matching policy and submit an issue title, body, and labels with an idempotency key

Steps:
1. Inspect the Action and Approval records
2. Re-submit the same idempotency key with a different title
3. Approve the original request

Expected: The first request is HELD with the exact normalized payload visible in the Action and Approval records; the changed replay is rejected with conflict; approval revalidates the credential and executes only the original payload.

## Test 9 - Hold and replay a Slack message write
Viewport: backend
Covers: F22 Slack side effect, bounded channel/message input, human approval, credential reauthorization
Description: Verifies a Slack message cannot be posted until an authorized human approves the exact normalized payload.

Setup:
1. Connect a Slack workspace with a token that can post messages
2. Declare `slack.messages.create` for an active Agent
3. Submit a channel and message with an idempotency key

Steps:
1. Inspect the Action and Approval records
2. Approve the request

Expected: The request is held with the normalized channel and text, then reauthorized and posted once with the same payload.

## Test 10 - Apply a workforce template into draft setup
Viewport: desktop
Covers: F23 template catalog, GET workforce templates route family, POST template apply route family, draft Role/Worker/Job creation, persistence after refresh
Description: Verifies an SMB can choose a built-in blueprint and receive durable draft workforce records without silently activating work.

Setup:
1. Register one unbound Agent Identity and connect the integrations needed by the Developer Assistant template

Steps:
1. Open Workforce and choose Developer Assistant from Workforce Templates
2. Select the unbound Agent Identity, keep the Worker name, choose an Engineering department, and create the draft setup
3. Refresh Workforce and open Jobs

Expected: The Worker remains DRAFT after refresh, its template Role and capability-ready example Jobs exist as DRAFT records, and no Job or Worker is automatically activated or queued.

## Test 11 - Keep missing template authority explicit
Viewport: desktop
Covers: template readiness, missing integration/capability blocker, no automatic integration connection, no automatic capability declaration, no automatic policy or approval creation
Description: Verifies convenience setup fails safe when a template depends on tools or scopes the organization has not connected.

Setup:
1. Register one unbound Agent Identity in an organization with no Gmail integration

Steps:
1. Open Workforce Templates and inspect Customer Support Assistant
2. Apply the template to the unbound Agent Identity
3. Inspect the resulting Worker, Jobs, Integrations, Capabilities, Policies and Approvals surfaces

Expected: The Worker is created as DRAFT; Gmail-dependent Jobs are reported as blocked instead of having their requirements removed; no integration, capability declaration, policy or approval is created automatically.

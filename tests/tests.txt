# Tests

## Test 1 - Route a final managed Job failure to its supervisor [sanity]
Viewport: desktop
Covers: final Run failure escalation, Worker supervisor routing, escalation inbox persistence, push-attempt state
Description: Verifies failed autonomous work becomes durable human supervision work instead of disappearing into runtime history.

Setup:
1. Create an ACTIVE Worker with the signed-in user as supervisor and an ACTIVE Job whose completion criteria cannot be satisfied by its bounded test observations

Steps:
1. Run the Job and allow the managed Run to reach its final FAILED state
2. Open Supervision → Mine
3. Select the new Job failure escalation and refresh the page

Expected: One OPEN Job failure escalation remains visible after refresh, names the Worker and Run, is assigned to the Worker's supervisor, and shows a durable push delivery state without exposing credentials.

## Test 2 - Escalate policy intervention and elevated risk without changing authorization
Viewport: desktop
Covers: policy escalation, HIGH/CRITICAL risk escalation, deterministic escalation rules, Action Gateway boundary
Description: Verifies autonomous policy/risk attention creates supervisor work while the original security decision remains authoritative.

Setup:
1. Configure a managed Job action whose policy returns REQUIRE_APPROVAL and whose effective risk reaches HIGH

Steps:
1. Process the Work Item until the Run waits for approval
2. Open Supervision → All and inspect the policy and risk escalations for the same Run
3. Disable the HIGH-risk escalation rule and leave policy escalation enabled

Expected: The Run remains WAITING_APPROVAL, the policy and initial HIGH-risk escalations are separate durable records, changing an escalation rule does not approve or execute the Action, and future HIGH-risk events stop creating that class while policy escalation remains active.

## Test 3 - Cancel a waiting Run and block stale approval-time execution
Viewport: desktop
Covers: supervisor Run cancellation, Work Item cancellation, correlation cancellation guard, approval-time Action Gateway revalidation
Description: Verifies a supervisor can stop managed work without a stale pending approval later reaching the provider.

Setup:
1. Create a managed Run that is WAITING_APPROVAL and has a linked policy escalation

Steps:
1. Open the escalation, enter a reason, choose Cancel Run, and confirm the destructive action
2. Approve the previously pending approval from Approvals
3. Return to Runtime and Supervision

Expected: The Run and Work Item remain CANCELLED, unfinished Run steps are cancelled, the approved held Action is BLOCKED by the managed-run cancellation guard before provider execution, and the escalation records the supervisor intervention.

## Test 4 - Pause a Worker and create an F11 Incident from supervision
Viewport: desktop
Covers: worker pause intervention, incident handoff, incident linkage, separation of Workforce and Agent Identity
Description: Verifies supervisors can restrict future managed work and escalate into existing incident controls without silently changing identity credentials.

Setup:
1. Have an OPEN escalation for an ACTIVE managed Worker

Steps:
1. Enter a reason, choose Pause Worker, and confirm
2. From the same escalation choose Create Incident with a reason
3. Open Workforce and Incidents

Expected: The Worker is PAUSED while its Agent Identity binding remains intact, an OPEN Incident targets that Worker's Agent Identity through the existing incident domain, and the escalation displays the linked incident ID plus both intervention records.

## Test 5 - Use the supervisor inbox and alert enablement on mobile
Viewport: mobile
Covers: responsive Supervision UI, Mine/All filtering, notes, reassignment validation, explicit notification subscription UX, API v2 normalization
Description: Verifies supervision remains usable on a phone and push enablement occurs only from explicit user action.

Setup:
1. Have at least one escalation assigned to the signed-in user and one escalation assigned to another organization member

Steps:
1. Open mobile navigation → Supervision, switch to API v2, and toggle Mine then All
2. Add a supervisor note and attempt reassignment to a non-member user ID
3. Tap Enable mobile alerts

Expected: The mobile inbox has no horizontal clipping, Mine shows only the signed-in user's assignments, the note persists, non-member reassignment is rejected visibly, and alert enablement either grants notifications or surfaces browser/platform guidance without silently subscribing on page load.

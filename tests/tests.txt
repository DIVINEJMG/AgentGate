# Tests

## Test 1 - Execute an allowed GitHub read through the Action Gateway [sanity]
Viewport: desktop
Covers: POST /api/v1/organizations/:organizationId/action-gateway/tests, shared agent credential validation, idempotency establishment, capability resolution, Policy Engine enforcement, GitHub adapter read execution, GET /api/v1/organizations/:organizationId/actions
Description: Verifies the primary Foundation 7 path reaches GitHub only after an authenticated agent receives ALLOW.

Setup:
1. Sign in and create "QA Operations" if no organization exists
2. Connect public repository "DIVINEJMG/AgentGate" if it is not already connected
3. Register "QA Gateway Agent", copy its one-time agent credential, and keep that value for this test
4. Declare `github.repository.metadata.read` for "QA Gateway Agent"
5. Create an enabled ALLOW policy named "Allow gateway metadata" for that agent, the AgentGate repository and `github.repository.metadata.read`

Steps:
1. Open Actions, select "QA Gateway Agent", the AgentGate repository and `github.repository.metadata.read`
2. Paste the copied agent credential and run the generated idempotency key through the gateway
3. Inspect the resulting Action Detail and recent action history

Expected: The action status is EXECUTED, policy outcome is ALLOW, a GitHub repository metadata summary/result is visible, and the action shows a correlation ID plus hashed idempotency identifier.

## Test 2 - Block a request when policy does not allow it
Viewport: desktop
Covers: default-deny enforcement, provider non-execution on DENY, persisted blocked action state
Description: Verifies a valid agent credential and capability declaration cannot bypass the Policy Engine.

Setup:
1. Use an active QA agent with a copied credential and connected AgentGate repository
2. Declare `github.repository.issues.read` for the agent but do not create an enabled matching issues policy

Steps:
1. Open Actions and select the QA agent, AgentGate repository and `github.repository.issues.read`
2. Paste the valid agent credential, generate a fresh idempotency key and run through the gateway
3. Inspect Action Detail

Expected: The action is BLOCKED with policy outcome DENY/default deny, no provider result is shown, and the blocked attempt appears in recent action history.

## Test 3 - Hold REQUIRE_APPROVAL without provider execution
Viewport: desktop
Covers: REQUIRE_APPROVAL enforcement, held action persistence, approval handoff boundary
Description: Verifies an approval-gated policy cannot accidentally execute before Foundation 8 supplies a human decision.

Setup:
1. Use an active QA agent with copied credential and declare `github.repository.pull_requests.read`
2. Create an enabled REQUIRE APPROVAL policy named "Review PR reads" for that agent/repository/scope

Steps:
1. Open Actions, select the QA agent, AgentGate repository and `github.repository.pull_requests.read`
2. Paste the valid credential and run a fresh idempotency key
3. Inspect Action Detail and recent actions

Expected: The action is HELD with policy outcome REQUIRE APPROVAL, no GitHub result is present, and the UI states that approval execution belongs to Foundation 8.

## Test 4 - Replay the same idempotent request without a second provider action
Viewport: desktop
Covers: idempotency replay, request fingerprint conflict protection, durable action identity
Description: Verifies sequential retries with the same agent, resource, scope and idempotency key return the original action record.

Setup:
1. Use the allowed metadata-read setup from the primary workflow and keep the same agent credential available

Steps:
1. Execute an allowed metadata read and note its action ID/correlation ID while keeping the idempotency key unchanged
2. Paste the same agent credential again and submit the exact same request with the unchanged idempotency key
3. Inspect the selected history item

Expected: AgentGate returns the same action record/correlation state instead of creating a second provider execution; reusing that key for a different scope is rejected.

## Test 5 - Reject an invalid agent credential on mobile while API v2 remains compatible
Viewport: mobile
Covers: agent-authentication guardrail, responsive Action Gateway form/history, POST /api/v2/organizations/:organizationId/action-gateway/tests, GET /api/v2/organizations/:organizationId/actions, v1/v2 action adapters
Description: Verifies mobile operators cannot execute using an invalid non-human credential and the same action model is readable through API v2.

Setup:
1. Sign in with an organization containing an active agent and connected GitHub resource

Steps:
1. On mobile open Actions and switch Compatibility view to API v2
2. Select an agent/resource/scope, enter `agt_sk_invalidcredentialvalue1234567890` and run a fresh idempotency key
3. Observe the error and action history

Expected: A visible invalid-agent-credential error is shown, no provider result is created from the invalid credential, API v2 remains selected, and the Actions layout remains usable on mobile.

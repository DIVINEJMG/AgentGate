# Tests

## Test 1 - Save workspace settings and retain the product profile [sanity]
Viewport: desktop
Covers: GET /api/v1/organizations/:organizationId/product, PUT /api/v1/organizations/:organizationId/settings, workspace rename, security contact persistence, organization controls
Description: Verifies an owner/admin can productize the workspace profile and the durable values are reflected after reload.

Steps:
1. Open Settings and set workspace name to `AgentGate QA Workspace`, security contact to `security@example.com`, and company URL to `https://example.com`
2. Save workspace settings
3. Refresh the page and return to Settings

Expected: The renamed workspace is shown in the application and Settings retains `security@example.com` and `https://example.com` with a successful readiness update.

## Test 2 - Show real readiness and bounded usage without enforcing preview limits
Viewport: desktop
Covers: product readiness derivation, bounded operational analytics, advisory agent limit, existing security-control continuity
Description: Verifies product analytics reflect current AgentGate state and the preview catalog does not disable existing controls.

Steps:
1. Open Settings in an organization that already has AgentGate control-plane records
2. Review readiness, agent/integration/policy/action counts and the 30-day activity metrics
3. Inspect the current preview-plan note

Expected: Readiness and usage are visible from existing records; any truncated window is disclosed, and the UI states that plan limits are observe-only/advisory rather than enforced.

## Test 3 - Present the commercial catalog without a fake checkout
Viewport: desktop
Covers: Free/Team/Business/Scale catalog, billing-provider boundary, no-checkout guardrail
Description: Verifies the product exposes pricing structure while accurately representing that no payment processor is connected.

Steps:
1. Open Settings and scroll to Plans & Billing Boundary
2. Review Free, Team, Business and Scale pricing cards
3. Inspect the billing status message

Expected: Four plan cards are visible; the current preview plan is identified, `OBSERVE ONLY` is visible, and there is no active checkout/purchase control.

## Test 4 - Use Foundation 12 through API v2 and persist workspace changes
Viewport: desktop
Covers: GET /api/v2/organizations/:organizationId/product, PUT /api/v2/organizations/:organizationId/settings, v2 productization adapter
Description: Verifies v2 exposes the same canonical workspace, readiness, commercial and usage state.

Steps:
1. Switch Settings to API v2
2. Change the company URL to `https://example.org` and save
3. Refresh Settings while API v2 remains selected

Expected: The updated URL persists, readiness/usage/plans render without contract-shape errors, and API v2 remains usable.

## Test 5 - Use product settings and operator docs on mobile
Viewport: mobile

# Tests

## Test 1 - Discover canonical capabilities from a connected GitHub repository [sanity]
Viewport: desktop
Covers: GET /api/v1/organizations/:organizationId/capabilities, GitHub capability projection, canonical resources/actions/scopes, live-integration filtering
Description: Verifies a real connected GitHub repository becomes a canonical resource with version-neutral action and scope descriptors.

Setup:
1. Sign in and create "QA Operations" if no organization exists
2. In Integrations, connect public repository "DIVINEJMG/AgentGate" if it is not already connected

Steps:
1. Open Capabilities
2. Select "DIVINEJMG/AgentGate" in the Resource catalog
3. Inspect its Action surface

Expected: One reachable GitHub repository resource is visible with read actions for metadata, issues and pull requests, including scopes `github.repository.metadata.read`, `github.repository.issues.read`, and `github.repository.pull_requests.read`.

## Test 2 - Declare capability scopes for an agent and retain them
Viewport: desktop
Covers: GET and PUT /api/v1/organizations/:organizationId/agents/:agentId/capabilities, capability declaration persistence, scope validation against live tenant catalog
Description: Verifies an agent can declare supported scopes without receiving authorization and the declaration persists after refresh.

Setup:
1. Sign in with "QA Operations"
2. Register "QA Research Agent" in Agents if it does not already exist
3. Ensure public repository "DIVINEJMG/AgentGate" is connected

Steps:
1. Open Capabilities and select "QA Research Agent"
2. Check `github.repository.metadata.read` and `github.repository.issues.read`, then save the declaration
3. Refresh, return to Capabilities, and select "QA Research Agent"

Expected: Both scopes remain checked after refresh and the page still states authorization is unresolved / no execution is enabled.

## Test 3 - Consume and update the same capability profile through API v2
Viewport: desktop
Covers: GET /api/v2/organizations/:organizationId/capabilities, GET and PUT /api/v2/organizations/:organizationId/agents/:agentId/capabilities, v1/v2 capability adapters
Description: Verifies the current v2 contract resolves to the same canonical resources and agent declaration as v1.

Setup:
1. Sign in with an organization containing a GitHub connection and at least one agent

Steps:
1. Open Capabilities and switch Compatibility view to "API v2"
2. Select the agent and add `github.repository.pull_requests.read`
3. Save the declaration and inspect the selected resource

Expected: API v2 remains selected, the same resource/actions are visible, the new pull-request scope is checked, and authorization remains unresolved.

## Test 4 - Remove disconnected resources from the live capability catalog
Viewport: mobile
Covers: live capability filtering, disconnected integration guardrail, mobile Capabilities behavior
Description: Verifies AgentGate does not advertise technical capability from a provider connection that is no longer reachable.

Setup:
1. Sign in with an organization containing a GitHub connection

Steps:
1. On mobile, open Integrations, select the GitHub connection, tap Disconnect, and confirm
2. Open Capabilities
3. Inspect the Resource catalog and any existing agent declaration

Expected: The disconnected repository is absent from reachable resources; any previously declared scopes backed only by that resource are shown as stale rather than active.

## Test 5 - Sign out hides private capability state
Viewport: desktop
Covers: authentication boundary, protected capability APIs, private capability declarations
Description: Verifies capability catalog and agent declaration state remain behind authenticated organization membership.

Steps:
1. Sign in with an organization and open Capabilities
2. Use the account control to sign out
3. Observe the resulting screen

Expected: The secure sign-in screen is shown and no organization resources, scopes, or agent capability declarations remain visible.

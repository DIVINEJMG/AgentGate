# Tests

## Test 1 - Trace an approval-gated action end to end in Audit [sanity]
Viewport: desktop
Covers: action.requested/action.held, approval.requested/approved, approved execution audit emission, GET /api/v1/organizations/:organizationId/audit, correlation tracing
Description: Verifies Foundation 9 reconstructs one approval-gated action through a shared correlation ID.

Setup:
1. Sign in to an organization with a connected public DIVINEJMG/AgentGate repository
2. Register an active QA Audit Agent and copy its credential
3. Declare `github.repository.pull_requests.read`
4. Create a REQUIRE APPROVAL policy for that agent, resource and scope

Steps:
1. Run the pull-request read through Actions and approve the resulting held request in Approvals
2. Open Audit and locate the newest action/approval events
3. Select one correlated event and choose "Trace this correlation"

Expected: The filtered timeline contains the same correlation ID across the agent action request, held/approval events, human approval and final executed action, with actor/resource/outcome details visible.

## Test 2 - Record a blocked action without provider execution
Viewport: desktop
Covers: action.requested/action.blocked audit events, default-deny observability, severity filtering
Description: Verifies a denied action produces a warning-level forensic record without a provider result.

Setup:
1. Use an active agent with a declared GitHub issues-read scope but no matching ALLOW policy

Steps:
1. Run the issues-read action through the gateway with a valid agent credential
2. Open Audit and set category to action and severity to warning, then Apply
3. Select the blocked event

Expected: A warning action.blocked event is visible with DENY/default-deny context and the action's correlation ID; no successful provider outcome is claimed.

## Test 3 - Record human policy changes in the audit ledger
Viewport: desktop
Covers: policy.created/policy.updated/policy.status.changed management audit emission, actor attribution, text search
Description: Verifies policy administration leaves human-attributed audit records.

Steps:
1. Create a policy named "QA Audit Policy", then edit it and disable it
2. Open Audit, search for "QA Audit Policy" and Apply
3. Inspect the matching policy events

Expected: Policy create/update/status events identify a human actor, the policy resource, revision/outcome metadata and timestamps.

## Test 4 - Filter one bounded audit window through API v2
Viewport: desktop
Covers: GET /api/v2/organizations/:organizationId/audit, category/severity/search filters, bounded window summary, v1/v2 normalization
Description: Verifies the current API contract exposes filtered events and operational summary without scanning unbounded history.

Steps:
1. Open Audit and switch Compatibility view to API v2
2. Filter category to approval or action and Apply
3. Inspect the metric cards and event list

Expected: API v2 remains selected, visible/critical/warning/trace metrics match the filtered event set, and the UI does not require loading all historical pages.

## Test 5 - Use forensic search and empty-state handling on mobile
Viewport: mobile
Covers: responsive Audit navigation/detail, audit search guardrail, no-match empty state, mobile trace UX
Description: Verifies operators can investigate audit history from a phone without a desktop-only layout.

Steps:
1. On mobile open navigation and choose Audit
2. Search for `definitely-no-such-audit-event` and Apply
3. Clear the filters and select a real event if one exists

Expected: The no-match state is clearly visible, Clear restores the recent audit window, and event details/trace controls remain usable without horizontal clipping.

# Tests

## Test 1 - Create a role and managed worker bound to an Agent Identity [sanity]
Viewport: desktop
Covers: GET /api/v1/organizations/:organizationId/workforce, POST /api/v1/organizations/:organizationId/workforce/roles, POST /api/v1/organizations/:organizationId/workforce/workers, Worker↔Agent Identity binding, role defaults, supervisor, working-hours persistence
Description: Verifies the primary F13 workflow creates a reusable role and a draft business-facing Worker anchored to an existing security identity.

Setup:
1. In Agents, register an active Agent Identity named `F13 QA Agent`

Steps:
1. Open Workforce and create role `QA Analyst` with purpose `Review operational quality`, responsibility `Review daily quality signals`, instructions `Prepare concise findings`, and recommended scope `github.repository.metadata.read`
2. Create worker `Maya QA`, bind `F13 QA Agent`, select `QA Analyst`, set department `Quality`, keep the current signed-in human as supervisor, and save Monday-Friday working hours
3. Refresh Workforce and select `Maya QA`

Expected: `Maya QA` persists as DRAFT with role `QA Analyst`, department `Quality`, the current human supervisor, the bound Agent Identity, inherited role responsibility/instructions, and visible working hours; the recommended scope is shown only as role metadata and has not granted a capability.

## Test 2 - Edit a worker and change workforce lifecycle without mutating Agent Identity
Viewport: desktop
Covers: PUT /api/v1/organizations/:organizationId/workforce/workers/:workerId, POST /api/v1/organizations/:organizationId/workforce/workers/:workerId/status, worker lifecycle separation from Agent Identity
Description: Verifies worker management state is durable and remains separate from the security identity lifecycle.

Setup:
1. Create an active Agent Identity, a workforce role, and a draft worker bound to that identity through the UI

Steps:
1. Edit the worker department, responsibilities, instructions and working hours and save
2. Activate the worker, then pause it
3. Open Agents and inspect the bound Agent Identity

Expected: Workforce retains the edited profile and PAUSED status while the bound Agent Identity remains ACTIVE; the UI explains that Worker lifecycle does not replace Agent/Incident security controls.

## Test 3 - Prevent a second managed worker from reusing a bound Agent Identity
Viewport: desktop
Covers: one-to-one Worker↔Agent Identity guardrail, POST workforce worker validation, safe identity selection
Description: Verifies a security Agent Identity cannot silently represent multiple non-archived managed workers.

Setup:
1. Create `F13 Bound Agent`, a role, and one managed worker bound to that Agent Identity

Steps:
1. Open Create worker again
2. Inspect the Agent Identity selector
3. Attempt to choose an identity for the second worker

Expected: `F13 Bound Agent` is unavailable for the second worker because it is already bound; no duplicate managed-worker binding can be created.

## Test 4 - Edit roles and workers through API v2 compatibility
Viewport: desktop
Covers: GET /api/v2/organizations/:organizationId/workforce, PUT /api/v2/organizations/:organizationId/workforce/roles/:roleId, PUT /api/v2/organizations/:organizationId/workforce/workers/:workerId, POST /api/v2/organizations/:organizationId/workforce/workers/:workerId/status, v2 workforce adapters
Description: Verifies v2 maps to the same canonical Workforce domain.

Setup:
1. Create a workforce role and draft worker through the UI

Steps:
1. Switch Workforce to API v2 and edit the role purpose/default instructions
2. Edit the worker profile and activate it
3. Refresh Workforce while API v2 remains selected

Expected: Role and worker changes persist, the worker is ACTIVE, and v2 renders the same business/security binding without contract-shape errors.

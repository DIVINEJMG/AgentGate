# Tests

## Test 1 - Configure and retain a recurring Job schedule [sanity]
Viewport: desktop
Covers: GET /api/v1/organizations/:organizationId/triggers, PUT /api/v1/organizations/:organizationId/jobs/:jobId/triggers, recurring schedule persistence, timezone handling, missed-run policy, Worker working-hours policy
Description: Verifies an operator can configure repeatable scheduled work without creating a Run or provider action.

Setup:
1. Create and activate a managed Worker and an ACTIVE Job named `F15 Scheduled Brief`

Steps:
1. Open Jobs → Triggers and select `F15 Scheduled Brief`
2. Enable a weekly schedule, choose Africa/Lagos, 08:30, Monday through Friday, `Queue one catch-up`, and `Queue for next working opening`, then save
3. Refresh the page and inspect the trigger configuration

Expected: The schedule remains enabled with the same timezone, time, weekdays and policies, a Next due timestamp is visible, and the page states that triggers create Work Items only.

## Test 2 - Internal event creates a durable queued Work Item
Viewport: desktop
Covers: POST /api/v1/organizations/:organizationId/triggers/events, internal-event trigger matching, trigger history, durable Work Item creation
Description: Verifies an authenticated internal event can create work while execution remains absent.

Setup:
1. Create and activate a managed Worker and ACTIVE Job named `F15 Event Job`
2. Configure internal event key `support.ticket.created` for the Job

Steps:
1. Open Jobs → Triggers, enter event key `support.ticket.created` and payload `{}`
2. Emit the event
3. Open Work Queue and then return to Triggers

Expected: A QUEUED Work Item exists for `F15 Event Job` with trigger type internal_event and Run not created yet, and Trigger History records a QUEUED internal-event outcome.

## Test 3 - Dependency trigger reacts to a job.completed event
Viewport: desktop
Covers: dependency Job configuration, `job.completed` internal event hook, dependency-trigger Work Item creation
Description: Verifies F15 exposes the completion-event contract that F16 can call after real runtime completion.

Setup:
1. Create ACTIVE Jobs named `F15 Upstream` and `F15 Downstream` for active managed Workers
2. Configure `F15 Downstream` to depend on `F15 Upstream`

Steps:
1. Open Jobs → Triggers and enter event key `job.completed`
2. Choose `F15 Upstream` as Source Job, leave Source Work Item as `qa-source-item`, and emit the event
3. Open Work Queue

Expected: `F15 Downstream` receives a QUEUED Work Item whose trigger type is dependency; no Run or provider execution is shown.

## Test 4 - Persist API trigger and show the credential boundary
Viewport: desktop
Covers: API-trigger configuration, Agent credential boundary, runtime POST /api/v1/runtime/organizations/:organizationId/jobs/:jobId/trigger contract
Description: Verifies API automation is explicitly opt-in and tied to the bound Agent Identity rather than a second trigger secret. The machine-to-machine runtime endpoint itself is intentionally not invoked by browser QA because its bearer credential is one-time secret material.

Setup:
1. Create an ACTIVE managed Worker with an ACTIVE Job

Steps:
1. Open Jobs → Triggers and enable authenticated API trigger
2. Save the trigger configuration
3. Refresh and inspect the API trigger section

Expected: API trigger remains enabled, the runtime POST endpoint is visible, and the UI states that the bound Agent Identity credential authenticates the trigger.

## Test 5 - Configure triggers through API v2 on mobile
Viewport: mobile
Covers: v2 Trigger workspace/config routes, responsive scheduler controls, interval scheduling
Description: Verifies the v2 adapter maps to the same canonical Scheduler domain on a phone-sized viewport.

Setup:
1. Create an ACTIVE managed Worker and ACTIVE Job named `F15 Mobile Job`

Steps:
1. Open mobile navigation → Jobs, switch to API v2, then open Triggers
2. Select `F15 Mobile Job`, enable an interval schedule every 30 minutes and API trigger, then save
3. Refresh the page

Expected: The v2 trigger configuration persists, the interval and API settings remain visible, and the trigger controls fit the mobile viewport without horizontal clipping.

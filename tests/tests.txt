# Tests

## Test 1 - Create, activate and manually queue a Job [sanity]
Viewport: desktop
Covers: GET/POST /api/v1/organizations/:organizationId/jobs, POST /api/v1/organizations/:organizationId/jobs/:jobId/status, POST /api/v1/organizations/:organizationId/jobs/:jobId/run-now, GET /api/v1/organizations/:organizationId/work-items, durable Job revision snapshot, manual queue boundary
Description: Verifies the primary F14 workflow turns a Worker responsibility into a durable queued Work Item without pretending the Managed Runtime exists.

Setup:
1. Create an ACTIVE managed Worker named `F14 QA Worker` with responsibility `Prepare daily quality summary` and an active bound Agent Identity

Steps:
1. Open Jobs and create `Daily Quality Summary` for `F14 QA Worker` with objective `Prepare the daily quality summary`, link the Worker responsibility, choose NORMAL priority, add completion criterion `Summary is ready for supervisor review`, and save
2. Activate the Job and click `Run now`
3. Open Work Queue, refresh the page and inspect the queued item

Expected: The Job persists as ACTIVE and the Work Queue contains a QUEUED item with the Job revision, Worker, priority, correlation ID and `Run not created yet`; no autonomous execution is presented as having occurred.

## Test 2 - Block activation when a required capability is not active
Viewport: desktop
Covers: required capability validation, activation readiness guardrail, Agent capability separation
Description: Verifies a Job requirement cannot silently become an Agent permission.

Setup:
1. Connect a GitHub integration so `github.repository.metadata.read` exists in the capability catalog
2. Create an ACTIVE Worker whose bound Agent does not declare `github.repository.metadata.read`

Steps:
1. Create a DRAFT Job for that Worker requiring `github.repository.metadata.read`
2. Attempt to activate the Job
3. Inspect the visible error and the Job state

Expected: Activation is rejected with a missing-active-capability message, the Job remains DRAFT, and no capability is automatically granted to the Agent.

## Test 3 - Edit, pause and resume a Job while preserving history
Viewport: desktop
Covers: PUT /api/v1/organizations/:organizationId/jobs/:jobId, Job revisioning, pause/resume lifecycle, Job history
Description: Verifies edits produce a new Job revision and lifecycle changes do not rewrite earlier queued snapshots.

Setup:
1. Create and activate a Job, then use Run now once so revision 1 has a queued history item

Steps:
1. Edit the Job objective and completion criteria and save
2. Pause the Job, then resume it
3. Inspect Job history

Expected: The Job revision increases, the Job returns to ACTIVE after resume, and the earlier Work Item still shows its original job revision instead of being rewritten by the edit.

## Test 4 - Cancel a queued Work Item
Viewport: desktop
Covers: POST /api/v1/organizations/:organizationId/work-items/:workItemId/cancel, queue state transition, durable cancellation
Description: Verifies humans can remove queued work before a runtime claims it.

Setup:
1. Create an ACTIVE Job and queue one Work Item using Run now

Steps:
1. Open Work Queue
2. Cancel the QUEUED Work Item
3. Refresh the page

Expected: The item persists as CANCELLED with its Job/Worker/correlation history intact and can no longer be cancelled again as a queued item.

## Test 5 - Use Jobs and Work Queue through API v2 on mobile
Viewport: mobile
Covers: GET/POST/PUT v2 Jobs routes, v2 Work Items routes, responsive Jobs navigation and forms
Description: Verifies the v2 adapter and phone-sized Jobs experience map to the same canonical domain.

Setup:
1. Create an ACTIVE managed Worker

Steps:
1. Open mobile navigation, choose Jobs and switch to API v2
2. Create a Job, edit it, activate it and use Run now
3. Switch to Work Queue and inspect the queued item

Expected: The v2 Job changes persist, the queued Work Item is visible with the same canonical fields, and Jobs/Queue controls remain usable without horizontal clipping.

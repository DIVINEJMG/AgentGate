# Tests

## Test 1 - Emergency-stop the organization and block a real gateway request [sanity]
Viewport: desktop
Covers: POST/GET /api/v1/organizations/:organizationId/execution-controls/:targetType/:targetId, organization kill switch, Action Gateway incident-control enforcement, execution restoration
Description: Verifies the organization emergency stop blocks new agent execution without deleting agent or integration state and can later be restored explicitly.

Setup:
1. Sign in to an organization with an active agent, copied agent credential, connected public DIVINEJMG/AgentGate repository, declared metadata-read scope and matching ALLOW policy

Steps:
1. Open Incidents and choose Emergency stop, entering reason `QA organization containment`
2. Open Actions and run the metadata-read request with the valid agent credential
3. Return to Incidents and restore organization execution with reason `QA containment cleared`

Expected: The action attempted while stopped is BLOCKED with an incident-control reason; after explicit restoration the organization execution banner returns to ACTIVE and agent/integration configuration remains present.

## Test 2 - Open an agent incident, suspend only that agent, then resolve independently
Viewport: desktop
Covers: POST/GET /api/v1/organizations/:organizationId/incidents, POST incident status, target execution control, incident lifecycle independence from recovery
Description: Verifies an incident record and an agent kill switch are separate durable states.

Steps:
1. Open a HIGH incident named `QA Agent Containment` targeting an existing active agent
2. Select the incident and choose Suspend target with reason `Unexpected QA behavior`, then Acknowledge and Resolve with note `Investigation complete`
3. Refresh Incidents and inspect the same incident

Expected: The incident remains RESOLVED with its resolution note while the target control can remain SUSPENDED until a separate Restore target action is performed.

## Test 3 - Block approval-time resume when an integration is suspended
Viewport: desktop
Covers: REQUIRE_APPROVAL held action, integration execution control, approval-time assertExecutionAllowed recheck, fail-closed recovery
Description: Verifies an approval cannot bypass a kill switch activated while the action waits.

Setup:
1. Use an active agent and connected GitHub integration with a declared pull-request-read scope and REQUIRE APPROVAL policy
2. Run the request so it becomes HELD and open an incident targeting that GitHub integration

Steps:
1. In Incidents suspend the integration target with reason `QA integration containment`
2. In Approvals approve the already-held action
3. Inspect the final action and incident control state

Expected: The approved action becomes BLOCKED rather than reaching GitHub because approval-time reauthorization detects the suspended integration.

## Test 4 - Use Incident Controls through API v2 and restore a target
Viewport: desktop
Covers: v2 incidents list/create/status contracts, v2 execution-control read/write normalization, explicit recovery
Description: Verifies the Foundation 11 compatibility adapter exposes the same canonical incident/control state through API v2.

Steps:
1. Switch Compatibility view to API v2 in Incidents and open a MEDIUM incident targeting an integration or agent
2. Suspend that target, acknowledge the incident, then restore the target with a recovery reason
3. Resolve the incident with a resolution note

Expected: API v2 remains selected; target control shows ACTIVE after explicit restoration and the incident shows RESOLVED without contract-shape errors.

## Test 5 - Manage containment from mobile without destructive configuration changes
Viewport: mobile
Covers: responsive Incident navigation, mobile emergency control, incident create/detail/lifecycle, target suspension and restoration
Description: Verifies an operator can perform the critical containment workflow from a phone-sized viewport.

Steps:
1. Open mobile navigation and choose Incidents
2. Open a LOW incident targeting an agent and use Suspend target
3. Restore the target and resolve the incident

Expected: Kill-switch state, incident lifecycle buttons and detail information remain usable without horizontal clipping, and the agent is not deleted or disabled by the incident-control workflow.

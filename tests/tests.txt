# Tests

## Test 1 - Require authentication before organization access [sanity]
Viewport: desktop
Covers: authentication gate, protected organization and integration APIs, anonymous access denial, SOT product identity
Description: Verifies anonymous visitors cannot reach tenant or integration state.

Steps:
1. Open AgentGate while signed out
2. Confirm the secure sign-in screen is shown
3. Confirm the screen identifies the product as "AgentGate" and "An SOT Product"

Expected: Organization, agent and integration data are not visible until secure sign in is completed.

## Test 2 - Retain organization and agent identity state
Viewport: desktop
Covers: organization membership boundary, agent registry, database persistence, human/agent identity separation
Description: Verifies prior foundations remain intact while the integration framework is added.

Steps:
1. Sign in and create "QA Operations" if no organization exists
2. Open Agents and register "QA Research Agent" if it does not already exist
3. Refresh and return to Agents

Expected: The organization and "QA Research Agent" remain visible after refresh and the agent retains its independent credential/lifecycle metadata.

## Test 3 - Connect and health-check a public GitHub repository
Viewport: desktop
Covers: GitHub adapter validateConnection, POST /api/v1/organizations/:organizationId/integrations/github, GET integration list, provider health check, database persistence, no-credential public mode
Description: Verifies the first real provider adapter validates and persists a public GitHub repository without storing a provider credential.

Steps:
1. Open Integrations and choose "Connect GitHub"
2. Enter "DIVINEJMG/AgentGate" and leave the optional token empty, then validate and connect
3. Select the connection, run "Check health", then refresh the page

Expected: "DIVINEJMG/AgentGate" remains visible as CONNECTED, health states the repository is reachable, and credential mode is shown as public/no credential.

## Test 4 - Consume integration state through API v2
Viewport: desktop
Covers: GET /api/v2 integration routes, v1/v2 integration adapters, canonical integration domain, API evolution
Description: Verifies API v2 presents the same provider connection through its newer response contract.

Steps:
1. Sign in with an organization containing a GitHub connection
2. Open Integrations and switch Compatibility view to "API v2"
3. Select the GitHub connection and inspect provider, health and credential posture

Expected: The same GitHub connection remains visible and its provider, resource, health and credential boundary are unchanged under API v2.

## Test 5 - Reject invalid GitHub repository coordinates on mobile
Viewport: mobile
Covers: GitHub adapter validation guardrail, mobile integration form, SSRF-resistant fixed-provider input boundary
Description: Verifies the mobile connection form rejects arbitrary URLs instead of treating them as provider endpoints.

Steps:
1. Open Integrations on mobile and tap "Connect GitHub"
2. Enter "https://example.com/private/repo" as Repository
3. Tap "Validate & connect"

Expected: A visible error says the repository must use owner/repository format and no integration is created.

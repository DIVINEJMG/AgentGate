# Tests

## Test 1 - Approve a held GitHub read and resume execution [sanity]
Viewport: desktop
Covers: POST /api/v1/organizations/:organizationId/action-gateway/tests, automatic approval creation, GET /api/v1/organizations/:organizationId/approvals, POST /api/v1/organizations/:organizationId/approvals/:approvalId/decision, safe held-action resume, GitHub read execution
Description: Verifies the primary Foundation 8 workflow persists REQUIRE_APPROVAL, waits for a human, revalidates the action and executes only after approval.

Setup:
1. Sign in and create "QA Operations" if no organization exists
2. Connect public repository "DIVINEJMG/AgentGate" if it is not already connected
3. Register "QA Approval Agent", copy its one-time credential, and declare `github.repository.metadata.read`
4. Create an enabled REQUIRE APPROVAL policy named "Review metadata reads" for that agent, repository and scope

Steps:
1. In Actions run `github.repository.metadata.read` with the copied agent credential and a fresh idempotency key
2. Open Approvals, select the new pending approval and click "Approve & resume"
3. Inspect the approval decision and execution result

Expected: The approval becomes APPROVED, execution becomes EXECUTED, the original action receives a GitHub metadata result, and the approval shows a reauthorization outcome that is not DENY.

## Test 2 - Reject a held action without provider execution
Viewport: desktop
Covers: rejection lifecycle, immutable human decision, held-action blocking, provider non-execution
Description: Verifies a reviewer can permanently reject a pending action and no provider call occurs afterward.

Setup:
1. Use an active QA agent with a copied credential, declared `github.repository.issues.read`, and a matching REQUIRE APPROVAL policy

Steps:
1. Run a fresh issues-read request through Actions so it becomes HELD
2. Open Approvals, select the pending record, enter "Not needed" and click Reject
3. Inspect the decision and corresponding action history

Expected: The approval becomes REJECTED, execution becomes BLOCKED, the decision note is retained, and the action has no provider result.

## Test 3 - Fail closed when the agent credential changes while approval waits
Viewport: desktop
Covers: approval-time agent revalidation, credential-fingerprint binding, stale-authority protection
Description: Verifies human approval cannot revive a request authenticated by a credential that was rotated while the action was held.

Setup:
1. Create a fresh held metadata-read approval using an active QA agent and REQUIRE APPROVAL policy

Steps:
1. Before deciding the approval, rotate the QA agent credential from the Agents screen
2. Return to Approvals and click "Approve & resume" on the still-pending record
3. Inspect the approval execution result and action history

Expected: The human decision is APPROVED but execution is BLOCKED because the initiating credential fingerprint changed; no GitHub provider result is created.

## Test 4 - Refuse to reverse an already decided approval
Viewport: desktop
Covers: immutable approval decision guardrail, decision retry safety, conflict response
Description: Verifies a completed human decision cannot be flipped to the opposite outcome.

Setup:
1. Create a fresh held approval and reject it through the Approvals screen

Steps:
1. Confirm the record shows REJECTED
2. Attempt the opposite approve decision for the same approval through the same v1 decision endpoint/workflow
3. Refresh the approval queue

Expected: AgentGate returns a visible conflict/error for the opposite decision, and the persisted approval remains REJECTED with the action still BLOCKED.

## Test 5 - Review and decide approvals on mobile with API v2
Viewport: mobile
Covers: GET /api/v2/organizations/:organizationId/approvals, POST /api/v2/organizations/:organizationId/approvals/:approvalId/decision, v1/v2 approval adapters, responsive approval queue/detail, notification opt-in control
Description: Verifies Foundation 8 remains usable from a phone and exposes push alerts only as an explicit user choice.

Setup:
1. Sign in with an organization that has a fresh pending approval

Steps:
1. On mobile open Approvals and switch Compatibility view to API v2
2. Inspect the pending approval, the Push alerts control and the held-action details
3. Reject the pending approval from the mobile decision panel

Expected: API v2 remains selected, the approval becomes REJECTED/BLOCKED, the queue and detail panels remain usable at mobile width, and push notification enablement is presented as an explicit control rather than an automatic permission request.

# Tests

## Test 1 - Assess a fresh agent without lowering capability risk [sanity]
Viewport: desktop
Covers: GET /api/v1/organizations/:organizationId/risk, POST /api/v1/organizations/:organizationId/risk-assessments, baseline/effective risk invariant, Risk UI
Description: Verifies a fresh agent receives an explainable deterministic assessment and risk never drops below the provider capability baseline.

Setup:
1. Sign in to an organization with a connected public DIVINEJMG/AgentGate repository
2. Register a fresh active agent named "QA Risk Fresh" and declare `github.repository.metadata.read`

Steps:
1. Open Risk and select QA Risk Fresh, the connected repository and metadata-read scope
2. Choose "Assess risk"
3. Inspect the transition and signal list

Expected: The result shows baseline low and effective risk low or higher, never lower than baseline, with each signal showing its count, threshold and reason; no GitHub provider action is executed by the dry run.

## Test 2 - Escalate burst activity into policy enforcement
Viewport: desktop
Covers: runtime behavior scoring, burst_activity threshold, effective risk passed to Policy Engine, Action Gateway block path, risk.assessed audit emission
Description: Verifies repeated requests can raise a low capability to medium and change the authorization outcome.

Setup:
1. Register a fresh active agent named "QA Risk Burst", copy its credential and declare `github.repository.metadata.read`
2. Create an ALLOW policy matching QA Risk Burst, the repository, metadata-read scope and risk `low` only

Steps:
1. Run four metadata-read gateway requests with unique idempotency keys
2. Run a fifth metadata-read request inside ten minutes with another unique idempotency key
3. Open Risk and inspect the newest QA Risk Burst assessment

Expected: The fifth assessment activates burst activity at 5/5, effective risk is medium, the low-only ALLOW policy no longer matches and the fifth action is blocked by default deny; the assessment is visible in Risk and correlated audit history.

## Test 3 - Make Decision Lab use effective behavioral risk
Viewport: desktop
Covers: POST /api/v1/organizations/:organizationId/policy-evaluations, risk-aware policy dry run, explainable risk in Policy Decision Lab
Description: Verifies human policy dry runs use the same deterministic effective-risk calculation as runtime execution.

Setup:
1. Use an agent with an active behavior signal and a declared GitHub scope

Steps:
1. Open Policies and select the agent, connected repository and declared scope in Decision Lab
2. Choose Evaluate
3. Inspect the decision card

Expected: The decision card shows baseline → effective risk and active signal names, and policy matching reflects the effective risk rather than only the static provider baseline.

## Test 5 - Use Risk safely on mobile and surface assessment failure
Viewport: mobile
Covers: responsive Risk navigation/lab/detail, risk assessment API failure handling, mobile guardrail
Description: Verifies phone users can inspect risk and that assessment failures are visible rather than treated as low risk.

QA Faults:
```json
[
  {
    "method": "POST",
    "path": "/api/v1/organizations/*/risk-assessments",
    "status": 503,
    "body_json": { "error": "simulated_risk_unavailable" }
  }
]
```

Steps:
1. On mobile open navigation and choose Risk
2. Select a valid agent, resource and scope and choose Assess risk
3. Inspect the resulting error state and existing risk history layout

Expected: A visible risk-assessment error is shown instead of a successful/low result, and metrics, runtime assessment list and detail/lab controls remain usable without horizontal clipping.

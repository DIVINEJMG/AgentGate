# Tests

## Test 1 - Show worker run outcomes and duration analytics [sanity]
Viewport: desktop
Covers: Performance workspace, GET performance route family, Worker summary, run success/failure rates, run durations
Description: Verifies completed and failed managed Runs become visible operational metrics without creating a worker score.

Setup:
1. Create one managed Worker and produce at least one COMPLETED Run and one FAILED Run for that Worker through the existing Jobs/Runtime workflow

Steps:
1. Open Performance
2. Inspect the top metrics and Worker summary row
3. Refresh the page

Expected: The Worker remains visible with the same Run counts, success/failure percentages and duration values after refresh, and the page states that no employee quality score is used.

## Test 2 - Keep governance outcomes separate from provider reliability
Viewport: desktop
Covers: blocked Action analytics, approval rate, tool reliability denominator, read-only performance behavior
Description: Verifies policy blocks and approval holds are visible but are not incorrectly counted as provider failures.

Setup:
1. Produce one managed provider Action that EXECUTES, one Action that is BLOCKED by policy, and one Action that is HELD for approval
2. Resolve at least one approval decision through the existing Approvals workflow

Steps:
1. Open Performance
2. Inspect Approval rate and Blocked actions
3. Inspect Tool reliability for the connected provider

Expected: Approval and blocked counts are visible, Tool reliability uses only executed/provider-failed attempts, and blocked or held governance outcomes are displayed separately from provider failures.

## Test 3 - Roll up departments and human-supervision signals
Viewport: desktop
Covers: department overview, escalation rate, incident rate, Worker-to-Agent incident mapping
Description: Verifies F19/F11 supervision events are summarized as operations data without changing those source records.

Setup:
1. Create managed Workers in at least two departments
2. Produce an escalation for one Worker and an Incident targeting that Worker's Agent Identity

Steps:
1. Open Performance
2. Inspect the Departments panel
3. Compare the affected Worker/department with the escalation and incident summary metrics

Expected: Departments are grouped by their existing Worker department, the affected Worker/department shows its supervision counts, and the source escalation and Incident remain unchanged in their original workspaces.

## Test 4 - Filter the recent Worker activity timeline
Viewport: desktop
Covers: recent activity projection across Runs, Actions, Escalations and Incidents, Worker filter
Description: Verifies a human can inspect one managed Worker's operational history without a new analytics write model.

Setup:
1. Produce recent Run and governance activity for two different managed Workers

Steps:
1. Open Performance
2. Set the Activity Timeline filter to the first Worker
3. Change the filter to the second Worker

Expected: Each filter shows only activity attributed to the selected Worker, with event kind/status and recent occurrence time visible.

## Test 5 - Use Performance with API v2 on mobile
Viewport: mobile
Covers: API v2 performance normalization, mobile Performance navigation, responsive metrics/worker/tool/activity views, bounded-window warning
Description: Verifies workforce operations analytics remain usable on a phone and the v2 contract renders the same canonical metrics.

Setup:
1. Have at least one managed Worker with Run and Action history

Steps:
1. Open mobile navigation → Performance
2. Switch Compatibility view to API v2
3. Review metrics, Worker summary, Tool reliability and Activity Timeline

Expected: The same canonical analytics remain visible with no horizontal page clipping; wide Worker data scrolls inside its table container, and any truncated source window is disclosed instead of silently treated as complete history.
